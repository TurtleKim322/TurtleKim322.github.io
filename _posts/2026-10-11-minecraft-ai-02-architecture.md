**설계 초안이다.** 환경 어댑터, 정책, 학습기와 메모리는 모두 구현 전이며, 도식은 현재 구상한 역할 관계를 표현한다.

## 게임 환경과 에이전트의 경계

Minecraft는 블록, 엔티티, 시간과 게임 규칙을 가진 환경(Environment)이다. 에이전트(Agent)는 환경에서 받은 정보로 행동을 결정한다. 두 구성 요소 사이에는 게임별 데이터를 학습 코드가 다룰 수 있는 형태로 바꾸는 어댑터를 두려 한다.

이 경계를 두는 이유는 게임 접속 문제와 학습 알고리즘 문제를 분리하기 위해서다. 어떤 후보를 선택하든 초기화, 관측, 행동 실행, 종료 처리를 같은 계약으로 제공할 수 있어야 한다. 다만 API 모양이 같다고 동일한 실험이 되는 것은 아니다. 얻을 수 있는 정보와 행동의 의미가 다르면 과제 자체가 달라진다.

## 현재 구상 중인 전체 구조

![설계 초안: Minecraft와 환경 어댑터, 정책, 경험 수집 및 학습기 사이의 흐름]({{ '/assets/images/minecraft-ai/architecture.svg' | relative_url }})

직접 제작한 설계 도식이다. 상위 목표 선택기는 후반 단계의 확장 후보이며 초기 구현 범위에는 포함하지 않는다.

실행 루프는 어댑터에서 관측을 받고, 정책이 행동을 선택하고, 게임에 행동을 적용하는 순서다. 학습 루프는 그때의 경험을 일정량 모아 정책을 갱신한다. 평가할 때에는 정책 갱신을 멈춘 체크포인트를 사용해, 실행 중 학습 효과와 평가 결과가 섞이지 않도록 할 계획이다.

## Observation, Action, Reward의 계약

| 요소 | 초기 설계 후보 | 확인할 문제 |
| --- | --- | --- |
| Observation | 위치, 체력, 주변 블록 등의 구조화 정보 또는 화면 픽셀 | 선택한 도구가 실제로 제공하는 정보와 정책에 허용할 정보 |
| Action | 전진, 회전, 점프 등 제한된 행동 | 지속 시간, 동시 입력, 실패와 지연 처리 |
| Reward | 과제 성공 보상과 필요한 최소 보조 보상 | 보상만 늘리고 과제는 해결하지 않는 행동 |
| 종료 조건 | 성공·사망 등의 종료, 제한 시간 도달 | 환경 종료와 시간 제한의 구별 |

화면 픽셀만 사용하는 에이전트와 서버 상태를 직접 읽는 에이전트는 난도가 다르다. 디버깅용 전체 월드 정보가 정책 입력으로 흘러들어 가지 않도록 관측 목록을 명시하려 한다. 과거를 모두 볼 수 없는 부분 관측 문제도 있기 때문에, 필요하면 최근 관측을 묶거나 순환 신경망을 검토할 수 있다.

[Gymnasium의 Env API](https://gymnasium.farama.org/api/env/)는 `reset()`에서 관측과 정보를, `step()`에서 다음 관측·보상·`terminated`·`truncated`·정보를 반환한다. 성공·사망 같은 과제 종료와 시간 제한 같은 중단을 구분해야 가치 추정과 평가 기록의 의미를 보존할 수 있다. 구형 Gym의 단일 `done` 값을 새 API 이름으로만 바꾸는 방식은 피하려 한다.

## 정책과 학습 알고리즘

정책(Policy)은 관측에서 행동을 고르는 규칙이다. 강화학습(Reinforcement Learning)은 행동 뒤에 얻은 보상을 이용해 장기적인 누적 보상이 커지도록 정책을 개선하는 접근이다. 정책을 신경망으로 표현할 수 있지만, 신경망을 실행하는 것만으로 학습이 일어나는 것은 아니다.

첫 학습 알고리즘으로는 PPO를 검토하고 있다. PPO는 이전 정책에서 지나치게 크게 변하지 않도록 갱신을 제한하는 목적함수를 사용한다. 그렇다고 Minecraft에서 자동으로 안정적인 학습을 보장하지는 않는다. 행동 공간을 단순화하고 보상과 초기화가 올바른지 확인하는 일이 선행돼야 한다. 구현 후보는 [Stable-Baselines3의 PPO](https://stable-baselines3.readthedocs.io/en/master/modules/ppo.html)이며 아직 채택하거나 실행하지 않았다.

## 계층형 강화학습은 후속 단계

생존이라는 큰 목표를 매 프레임의 키 입력으로 직접 연결하면 탐색해야 할 경우의 수가 많아진다. 계층형 강화학습(Hierarchical Reinforcement Learning)은 상위 수준의 목표·기술 선택과 하위 수준의 행동 수행을 나누는 방향이다.

이 프로젝트에서는 상위 모듈이 ‘안전한 장소로 이동’ 같은 목표를 고르고, 하위 정책이 이동 행동을 수행하는 구조를 후보로 둔다. 목표를 언제 바꾸며 기술이 언제 끝나는지도 정의해야 한다. 단순히 함수를 여러 개로 나눴다고 계층형 **학습**이 구현되는 것은 아니다. 초기에는 단일 과제를 먼저 검증하고, 기술 선택을 학습할지 규칙으로 시작할지는 나중에 결정하려 한다.

## 경험 데이터와 Memory를 나누기

| 저장 대상 | 목적 | 보관 구상 |
| --- | --- | --- |
| Rollout | 최근 정책으로 얻은 전이로 PPO 갱신 | 학습 배치 단위의 임시 버퍼 |
| 에피소드 기록 | 실패 원인, 보상 구성, 재현 조건 확인 | 실행 ID·환경 설정과 함께 장기 보관 |
| 체크포인트 | 정책 복원과 평가 | 모델, 전처리 설정, 학습 설정을 함께 저장 |
| 경험 Memory | 목표별 성공·실패 요약과 기술 재사용 | 후속 단계에서 검색 및 갱신 규칙 설계 |

PPO는 기본적으로 현재 정책에 가까운 데이터로 학습하는 on-policy 방식이다. 과거 로그를 무제한으로 섞어 replay buffer처럼 다시 학습시키는 구조로 가정하지 않는다. 오래된 기록은 분석이나 별도의 모방학습 검토에 사용할 수 있지만, 그때에는 학습 절차도 달라진다. 또한 일화 기록을 저장하는 Memory와 정책 내부의 은닉 상태는 서로 다른 개념이다.

## LLM 에이전트와의 차이

LLM 기반 에이전트는 텍스트나 이미지로 상황을 해석하고, 도구 호출이나 코드 실행으로 작업을 수행하도록 구성할 수 있다. 강화학습 에이전트는 환경에서 수집한 전이와 보상을 이용해 행동 정책을 학습한다. 비교의 핵심은 “어느 쪽이 더 똑똑한가”보다 **무엇을 입력받고, 무엇을 출력하며, 어떤 과정에서 갱신되는가**다.

LLM이 실행 중 경험을 문서로 저장하거나 프롬프트에 추가한다고 모델 가중치가 자동으로 학습되는 것은 아니다. 반대로 LLM과 강화학습은 결합할 수 있다. 장기 목표 제안에 LLM을 쓰고 짧은 행동을 학습 정책에 맡기는 방식도 후보지만, 비용·지연·평가 문제가 늘어나므로 초기 필수 구성에는 넣지 않을 계획이다.
