**모든 내용은 수집 설계다.** 아직 게임 화면을 녹화하거나 행동 데이터를 수집하지 않았다. 아래 JSON은 형식을 설명하기 위해 만든 가상 예시이며, 실제 실행 결과나 성능 수치가 아니다.
{: .notice--info}

## AI가 보는 것과 사람이 보는 것

캐릭터가 벽 앞에서 멈췄다면 경로를 찾는 중인지, 행동 명령이 전달되지 않았는지, 정책이 같은 행동을 반복하는지 화면만으로는 구분하기 어렵다. 반대로 숫자 로그만 보면 주변 지형이나 충돌의 맥락을 놓치기 쉽다. 그래서 영상과 행동 기록을 함께 남기려 한다.

정책에 주는 내부 관측과 사람이 보는 관찰 화면은 구분할 계획이다. 구조화 관측을 쓰는 에이전트라면 위치·체력·주변 블록 등이 입력이고, 사용자는 별도 게임 클라이언트에서 캐릭터를 바라볼 수 있다. 픽셀 관측을 쓰는 경우에도 정책에 입력한 프레임과 편집·녹화된 영상이 항상 같은 시점이라고 가정할 수 없다.

관찰용 플레이어가 월드에 들어가면 게임 규칙이나 주변 로딩에 영향을 줄 수도 있다. 관전자 모드·별도 뷰어 사용 여부와 관찰 중 상호작용 금지 규칙을 검토하고, 평가 조건에 관찰 방식까지 기록하려 한다.

## 데이터 수집 구조

![설계 초안: 실행 식별자와 시간 기준을 공유하는 행동 로그, 영상 녹화, 저장소와 대시보드]({{ '/assets/images/minecraft-ai/data-flow.svg' | relative_url }})

직접 제작한 구조도다. 학습 실행은 게임 제어를 진행하고, 기록기는 이벤트를 저장한다. 디스크 쓰기 때문에 행동 주기가 흔들리지 않도록 버퍼링을 검토하되, 누락·지연 횟수를 별도로 남기려 한다. 원본 로그는 보존하고 집계 값은 다시 계산할 수 있게 만드는 것이 목표다.

## 녹화 도구 후보: OBS와 FFmpeg

| 도구 | 검토하는 활용 | 확인할 점 |
| --- | --- | --- |
| OBS Studio | 사용자가 보는 게임 창과 설명용 장면 녹화 | 캡처 방식, 해상도, 인코더, 프레임 손실과 자원 경합 |
| FFmpeg | 녹화 파일 변환, 구간 추출, 시간 정보 검사 및 자동화 | 입력 장치 지원, 영상 PTS 보존, 가변 프레임률과 인코딩 지연 |

[OBS 공식 시작 안내](https://obsproject.com/kb/quick-start-guide)를 따라 캡처와 인코딩 설정을 검토하고, 파일 후처리는 [FFmpeg 공식 문서](https://ffmpeg.org/ffmpeg.html)를 참고할 예정이다. 어느 도구도 게임 스텝과 영상 프레임을 자동으로 완벽히 맞춰 주지는 않는다. 초기에는 짧은 녹화로 시간을 대조한 뒤 장시간 녹화로 확장하려 한다.

## 식별자와 시간 기준

실행 전체를 `run_id`, 한 번의 초기화부터 종료까지를 `episode_id`, 그 안의 행동 단위를 `step_id`로 구분할 계획이다. 같은 에피소드 번호가 다른 실행에서 반복될 수 있으므로 세 값을 함께 사용한다. 스키마 버전도 넣어 필드가 바뀐 로그를 구별하려 한다.

사람이 읽는 Timestamp는 UTC ISO 8601 형식으로 남기고, 실행 중 경과 시간은 단조 증가 시계(monotonic clock)를 기준으로 삼으려 한다. PC 시각이 보정돼도 시간 간격을 안정적으로 계산하기 위해서다. Node.js와 Python이 서로 다른 시계를 사용한다면 두 값의 차이를 측정해야 하며, 서로 같은 원점을 가진다고 가정하지 않는다.

하나의 전이 기록은 행동 전 관측 `observation_before`, 요청한 행동, 실제 실행 결과, 행동 후 `observation_after`, 보상과 종료 상태로 구성한다. 명령 송신 시각과 결과 수신 시각을 따로 남겨 지연이나 타임아웃을 분석할 예정이다. 가능하다면 게임 tick도 추가하되, 현실 시간·환경 스텝·게임 tick을 같은 단위로 취급하지 않는다.

## 로그 형식 예시

다음 값들은 **필드 설명용 설계 예시**다. 위치와 보상은 임의로 정했으며, 학습 성과를 나타내지 않는다. 모든 후보가 체력이나 인벤토리를 제공하는 것도 아니다. 제공하지 않는 정보는 `null`과 수집 가능 여부로 표현할 계획이다.

```json
{
  "schema_version": 1,
  "example_only": true,
  "run_id": "design-example",
  "episode_id": 1,
  "step_id": 1,
  "timestamp_utc": "2026-10-11T00:00:00.000Z",
  "action_sent_ms": 0,
  "observation_received_ms": 200,
  "observation_before": {
    "position": [0.0, 64.0, 0.0],
    "health": 20,
    "inventory": []
  },
  "action": {"name": "move_forward", "requested_ticks": 4},
  "action_status": "completed",
  "observation_after": {
    "position": [0.0, 64.0, 0.3],
    "health": 20,
    "inventory": []
  },
  "reward": 0.0,
  "reward_components": {"task_success": 0.0},
  "episode_reward_so_far": 0.0,
  "terminated": false,
  "truncated": false,
  "video_segment_id": "example-segment-01",
  "video_pts_ms": 200,
  "sync_status": "example_unverified"
}
```

`requested_ticks`는 요청량이며 실제 경과 tick을 보장하지 않는다. 가능한 경우 실제 실행 tick을 별도 기록하고, 지원되지 않으면 측정 불가로 남긴다. 위 예시의 200ms 역시 동기화를 검증한 값이 아니다.

실행 설정에는 월드 시드, 게임·어댑터 버전, 정책 체크포인트 식별자, 보상 정의 버전도 연결할 예정이다. 로그인 토큰, 실제 계정 식별자와 사용자 이름이 포함된 로컬 절대 경로는 공개용 로그에 포함하지 않는다.

## Reward와 학습 지표

스텝 보상(Reward)은 한 행동 이후의 값이고, 에피소드 보상(Episode Reward)은 해당 에피소드에서 받은 보상의 합으로 정의하려 한다. 학습 알고리즘의 할인 누적 보상이나 가치 추정치와는 구분해 이름과 집계 방식을 문서화할 계획이다.

평가에서는 과제 성공률, 생존 시간, 완료까지의 스텝 수, 체력 손실과 자원 확보량 중 과제에 맞는 지표를 선택하려 한다. 학습 손실과 엔트로피는 학습 상태를 이해하는 보조 지표이지 플레이 능력 자체의 증거는 아니다. 평균만 보지 않고 여러 시드의 분포, 실패 비율과 평가 에피소드 수도 함께 남길 예정이다.

## CSV, JSONL, SQLite, Parquet 중 무엇을 쓸까

| 형식 | 적합한 데이터 | 고려할 비용 |
| --- | --- | --- |
| CSV | 에피소드별 보상·길이·성공 여부 요약 | 인벤토리 같은 중첩 구조는 펼치거나 별도 표로 분리해야 함 |
| JSONL | 중첩 관측과 이벤트의 줄 단위 원본 기록 | 반복 필드로 용량이 커지고 대량 조회에 비용이 듦 |
| SQLite | 실행·에피소드 메타데이터 및 조건 검색 | 여러 기록기의 동시 쓰기와 트랜잭션 주기 설계 필요 |
| Parquet | 많은 스텝을 열 단위로 읽는 통계 분석 | 스키마 관리와 일정량 모아 쓰는 과정 필요 |

초기안은 JSONL 원본과 CSV 요약으로 시작하고, 검색 필요가 생기면 SQLite, 대규모 분석에는 Parquet 변환을 검토하는 것이다. 네 형식을 처음부터 모두 운영할 계획은 아니다. 영상과 이미지 프레임은 별도 파일에 저장하고 로그에는 상대 경로 또는 자산 ID를 두려 한다.

## 영상과 행동 데이터의 시간 동기화

고정 30fps라고 해서 `프레임 번호 / 30`만으로 스텝 시각을 결정하면 프레임 손실이나 가변 프레임률에서 오차가 생길 수 있다. 실제 영상의 표시 시각(PTS)을 사용하고, 실행 시작 시점과 녹화 시작 시점의 차이를 메타데이터에 기록하려 한다.

초기에는 화면에 동기화 표식을 보여 주는 시점과 로그 이벤트를 대응시켜 오프셋을 측정하는 방법을 검토한다. 긴 녹화에서는 중간 표식으로 시간 드리프트도 확인해야 한다. 각 행동의 송신·수신 구간에 대응하는 영상을 찾아보되, 렌더링 지연 때문에 정확한 한 프레임 대응을 보장하지 못하면 오차 범위를 표시하려 한다. 녹화가 중단돼 새 파일이 생기면 구간별 오프셋을 다시 관리해야 한다.

## 대시보드 구상과 다음 단계

추후에는 실행을 선택하면 보상 그래프, 위치 변화와 해당 시점의 영상을 함께 볼 수 있는 대시보드를 검토하려 한다. 먼저 로그 스키마와 동기화 정확도를 확인한 뒤 UI를 만드는 순서가 맞다. 보기 좋은 그래프가 원본 데이터의 누락이나 잘못된 시간을 가려서는 안 된다.
