처음에는 파일 약 100MB, 비압축 합계 약 200MB, 15,000문단, 200만 문자 제한을 사용했다. 큰 문서를 선택할 수 있게 하려면 숫자를 늘리는 것만으로는 부족했다. 입력 컨테이너의 크기와 추출되는 텍스트·이미지·비교 결과의 크기가 서로 다르기 때문이다.

## 입력 허용과 처리 보장을 구분하기

| 자원 | 현재 한도 |
|---|---:|
| 파일당 입력 | 1 GiB |
| ZIP 비압축 합계 | 4 GiB |
| 블록 | 100,000 |
| 문자 | 50,000,000 |
| Windows 작업 프로세스 메모리 | 2 GiB |

여기서 1 GiB는 1,073,741,824바이트다. 그 이하를 선택할 수 있다는 뜻이며 모든 문서를 끝까지 처리한다는 뜻은 아니다. 압축 해제 합계나 텍스트 한도를 넘으면 오류를 안내한다. ZIP 압축 비율 방어도 유지했다.

## 큰 파일 전체를 복사하지 않기

PDF는 경로로 열어 페이지를 순차 처리한다. DOCX/HWPX는 zipfile로 컨테이너를 열고 필요한 XML entry를 64KiB씩 읽는다. 미디어가 많은 문서에서 이미지 전체를 메모리에 올릴 필요가 없다.

다만 입력 XML을 스트리밍한다고 비교 엔진도 상수 메모리가 되는 것은 아니다. 추출 블록은 설정된 한도 안에서 메모리에 남는다. HWP Automation은 전체 텍스트를 반환할 수 있다. 이 차이를 감추지 않고 별도의 자원 한도로 다뤘다.

## 비교와 화면에도 경계가 필요했다

전체 문자에 SequenceMatcher를 적용하지 않고 먼저 블록·청크 단위의 일치 영역을 찾는다. 청크 기준은 최대 1,000블록 또는 약 200만 문자이며 세부 비교 범위에도 한도가 있다. 같은 입력을 양쪽에 선택한 경우 문서 객체와 계산 결과를 재사용한다.

결과는 SQLite로 저장하고 Text View는 일부만 표시한다. 페이지 이미지는 현재 위치와 제한된 preload에만 만든다. 작은 입력 파일이라도 압축된 텍스트가 매우 크면 문제가 될 수 있으므로 파일 크기만 보고 안전하다고 판단하지 않는다.

## 취소와 오류가 정상 경로가 되도록

파서·비교 루프는 취소 상태를 확인한다. 작업 프로세스의 메모리를 제한하고, 메모리 부족이나 한도 초과를 UI에서 알린다. 취소한 작업의 임시 파일과 자식 프로세스를 정리하는 경로도 테스트했다. 모든 외부 프로그램의 강제 종료 상황까지 완벽히 복구한다고 보장할 수는 없다.

## 실제로 확인한 범위

자동 생성한 100MiB/500MiB DOCX, 1GiB HWPX, 3,000페이지 PDF를 앞선 대용량 검증에서 사용했다. 대형 컨테이너에는 미디어나 패딩이 포함될 수 있어 파일 크기가 곧 텍스트 규모는 아니다. 같은 파일을 양쪽에 넣은 재사용 성능도 서로 다른 두 문서의 성능과 구분했다.

이 자료는 저장소에 넣지 않고 생성 방식과 테스트 코드를 남긴다. 현재 상태는 “최대 입력 제한 확대 및 대용량 처리 구조 개선”이며, 임의의 1GB 실문서를 완벽하게 처리했다는 결론은 아니다.
