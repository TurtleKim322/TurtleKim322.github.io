대용량 시계열 분석에서는 Linux 내부 여유 공간과 Windows 시스템 드라이브의 여유 공간이 서로 다르게 보일 수 있다. 이 글은 프로젝트 작업 당시 WSL2에서 겪은 저장공간 부족과 복구 기록을 설명한다. 본문의 숫자는 현재 PC 상태가 아니라 당시 로그와 메모에 적힌 스냅샷이다.

## 저장 구조를 두 층으로 보기

WSL2의 Linux 배포판은 Windows 파일시스템 안의 가상 디스크(ext4.vhdx)에 저장된다. Linux에서 `df`가 보여 주는 것은 게스트 파일시스템의 용량·사용량이며, Windows C:에서 ext4.vhdx가 차지하는 물리 공간과 일대일로 같지 않다. 중간 산출물을 지워 Linux 내부 여유가 늘어도, 동적 가상 디스크 파일의 실제 크기가 즉시 줄어든다고 보장할 수 없다.

![WSL과 Windows 저장공간의 관계](/assets/images/insar-seoul/10-storage/wsl-storage-architecture.png)

그림 1. **개념도.** Windows 물리 저장공간, WSL2의 가상 디스크, Linux 파일시스템, 작업 파일의 포함 관계를 설명한다. 실제 사용량 측정값이나 복구 명령의 실행 결과는 아니다.

## 당시 관측값과 장애 흐름

작업 기록에는 입력 자료 묶음 `ZIP124`가 약 **546.3 GB**, StaMPS 작업 복사본 `stamps_final`이 약 **192 GB**로 적혀 있다. Windows C:의 여유 공간은 약 1 GB까지 줄었고, 이후 불필요한 중간 파일을 정리한 뒤 약 762 GB의 여유 공간을 확보했다고 기록되어 있다. 이 수치는 작업 당시 메모이므로 지금 파일이 존재하거나 같은 공간을 차지한다는 뜻이 아니다.

기록된 장애 흐름은 PS 후보와 중간 행렬 증가 → ext4.vhdx와 C: 공간 압박 → 입력·출력 I/O 오류와 Bus error, WSL 불안정 → 안전한 정리와 가상 디스크 관리 → compact 후 환경 복구다. 이 사례에서 중요한 점은 Linux 내부의 df만 보고 C:의 여유 공간을 판단하지 않는 것이다.

## 재현 가능한 점검 원칙

1. 처리 전 Windows 드라이브와 WSL 파일시스템의 여유 공간을 각각 기록한다.
2. 예상 산출물과 이미 완료된 결과를 구분하고, 대용량 작업 전에 백업 위치와 복구 가능성을 확인한다.
3. 파일을 지우기 전 대상 경로, 파일 소유 처리 단계, 크기, 다른 산출물에서의 재생성 가능성을 확인한다.
4. 처리 중인 입력·출력과 유일한 결과는 정리 대상으로 취급하지 않는다.
5. 정리 후에는 Linux 게스트 용량과 Windows 호스트 여유 공간을 다시 각각 측정한다.

가상 디스크 축소나 WSL 종료·재시작은 데이터와 실행 중 작업에 영향을 줄 수 있다. 이 글은 현재 시스템에서 그런 조치를 실행하라는 절차가 아니며, 작업 중인 StaMPS 실행을 중단하거나 자료를 임의 삭제하는 방법을 안내하지 않는다. 저장공간 관리는 각 단계의 백업과 완료 상태를 확인한 뒤 진행해야 한다.

이 시리즈의 처리 그림과 수치는 분석 근거를 남기기 위한 기록이다. 작업 디렉터리 전체나 개인 경로는 공개하지 않고, 필요한 파일명과 단계 정보만 설명했다.
