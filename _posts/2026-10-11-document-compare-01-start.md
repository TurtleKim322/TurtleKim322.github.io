문서 두 개를 놓고 수정한 부분을 찾는 일은 단순해 보인다. 하지만 Word에서 만든 문서와 PDF로 배포한 문서를 비교하면 줄과 페이지가 달라진다. 한글 파일까지 포함하면 같은 문장도 다른 구조로 저장된다. 이 프로젝트는 이런 차이를 사람이 검토할 수 있도록 정리하는 Windows 데스크톱 앱에서 출발했다.

## 텍스트 파일의 줄 비교에서 문서 비교로

텍스트 편집기의 줄 비교를 떠올리면 첫 구현은 쉬워 보인다. 같은 줄끼리 비교해 달라진 문자를 표시하면 된다. 문제는 문서의 줄이 내용의 단위와 같지 않다는 데 있다. 글꼴이나 페이지 폭이 바뀌면 내용이 같아도 줄은 달라진다. PDF에서 뽑은 텍스트는 작성자가 입력한 문단과도 일치하지 않을 수 있다.

Draftable 같은 좌우 문서 검토 도구에서 UI 아이디어를 얻었지만, 목표를 제품 전체 복제로 잡지는 않았다. 먼저 텍스트 차이를 찾고, 확인할 수 있는 변경은 실제 페이지 위에서 가리키는 MVP를 만들기로 했다. 원문을 대신 판정하기보다 검토 위치를 좁혀 주는 도구에 가깝다.

## Python과 PyQt6를 선택한 이유

Python에서는 문서 구조와 비교 알고리즘을 빠르게 실험할 수 있었고, PyQt6로 파일 선택과 좌우 화면을 하나의 데스크톱 앱으로 묶을 수 있었다. PDF에는 PyMuPDF, Word 예제와 테스트에는 python-docx를 사용했다. 이후 큰 DOCX를 다루면서 실제 본문 리더는 ZIP/XML 스트리밍 방식으로 바뀌었다.

언어를 정한 것보다 중요했던 선택은 공통 모델이었다. 각 형식의 파서는 텍스트와 위치 정보를 Block으로 만들고, 비교 엔진은 이 블록을 받는다. UI가 HWPX의 XML 태그나 PDF 추출 API를 직접 알아야 하는 구조를 피했다.

```text
DOCX / PDF / HWPX / HWP
  → 형식별 파서 → 공통 문서 모델
  → 문단 대응과 Diff → Text View / Page View
```

## 지금 가능한 범위

![문서 비교 프로그램의 원본·수정본 선택 화면](/assets/images/document-compare/01-file-selection.png)

0.4.2 앱의 Qt 화면을 예제용으로 렌더한 이미지다. 사용자 문서를 열지 않은 초기 화면이다.

0.4.2에서는 DOCX·PDF·HWPX 텍스트 비교, 교차 형식 대응, 검색과 변경 탐색, PDF 페이지 보기, 한글·영어 OCR을 구현했다. HWP는 한컴 Automation이 있는 환경에서만 사용할 수 있다. DOCX 원본 지면을 보려면 Word가, HWP/HWPX 지면을 보려면 한컴이 필요하다.

완성된 범용 문서 판독기를 뜻하지는 않는다. 그림만 바뀐 문서는 놓칠 수 있고, 서식이나 복잡한 표 구조도 완전 비교 대상이 아니다. 이 연재에서는 구현된 기능과 확인하지 못한 범위를 함께 기록한다. 소스는 별도 Private GitHub 저장소에서 관리하고, 공개 글에는 구조와 짧은 개념 예시만 남긴다.
